# Quartile-average-LLR RELDEC — run results (k = 3, 4, 5)

Date: 2026-09-11/12. Design rationale in `docs/notes/quartile_llr_reldec.md`
— this note is the actual run's numbers.

## Run configuration

- Matrix: `wran_384_256.mat` (128×384, row degree 10–11, rate 2/3)
- Interpreter: GNU Octave 11.1.0 (`apt-get install octave`, run with user's
  explicit go-ahead — MATLAB is not installed in this environment)
- Training: `numSamples = 30000` episodes, `lmax = 50` scheduling steps/episode,
  `alpha=0.1`, `beta=0.9`, `epsilon=0.1`, per k ∈ {3, 4, 5} — 90000 episodes
  total, ~58 min wall clock (16m/19m/23m for k=3/4/5 respectively — training
  time grows with k, as expected: `quartile_state_batch.m`'s per-step cost is
  independent of k, but a bigger `2^k`-row Q-table plus O(k) bin-packing work
  per state add up)
- Eval: `SNR_db = [0 1 2 3 4]`, 1000 frames/point, greedy policy (epsilon=0),
  scheduling budget `m*maxIter` = 128×5 = 640 actions/frame with early stop on
  zero syndrome — ~2h wall clock for all 3 k × 5 SNR × 1000 frames
- Raw logs: `scratch/quartile_llr_run/{train,eval,pipeline}.log`
- Saved: `external_ref/ldpc_rl/checkpoints/Q_wran_quartile_k{3,4,5}.mat`,
  `.../quartile_llr_eval_results.mat`, `.../quartile_llr_ber.png`

## Results

BER (bit error rate, over all 384 bits/frame, all-zero codeword — see the
"no Communications Toolbox" caveat in `quartile_llr_reldec.md`):

| k \ SNR (dB) | 0 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|---|
| 3 | 0.12358 | 0.09793 | 0.07253 | 0.05106 | 0.03326 |
| 4 | 0.12304 | 0.09739 | 0.07282 | 0.05095 | 0.03333 |
| 5 | 0.12401 | 0.09684 | 0.07302 | 0.05114 | 0.03315 |

FER (frame error rate) was **1.0 for every (k, SNR) cell** — every one of the
15000 frames had at least one residual bit error at the end of its 640-action
budget. This is consistent with the BER level, not a separate bug: at
BER ≈ 0.03–0.12 over 384 bits, the expected error count per frame is
~12–46 bits, so a fully error-free frame is essentially never sampled at these
SNRs/budget. Put another way: **this scheduler configuration does not drive
WRAN to a low-BER regime within a 640-action budget at 0–4 dB** — the reward
pushes the policy toward locally satisfying the acted-on cluster, but nothing
here demonstrates it reaches the near-zero-BER waterfall region other RELDEC
variants target. Whether that's a property of the quartile-average state
itself, the training sample/budget, or genuine under-decoding at this SNR
range/action budget is not established by this run — a direct comparison
against `reldec_test.m`'s own eval numbers on the same matrix would be needed
to say more, and wasn't run here (out of scope of what was asked).

## k has no measurable effect

The three curves are visually indistinguishable in `quartile_llr_ber.png` —
BER differs by ≤0.001 absolute between k=3, k=4, k=5 at every SNR point,
smaller than the sampling noise at 1000 frames (standard error of a BER
estimate at p≈0.12, n=384000 bits ≈ 0.0007). **Going from 3 to 5 quantile
groups per cluster makes no detectable difference to decoding performance in
this setup.** This is itself the headline finding of the sweep, not a null
result to explain away — the quartile-count design choice appears not to be a
sensitive parameter for this state/reward/matrix/SNR combination.

## Comparison against stored `rl/` (Python) RELDEC results

`experiments.db` has a stored, more-completed run of this repo's own Python
`reldec` (`rl/agents/reldec.py`, hard-decision state — **not** the MATLAB
`external_ref/` implementation) on the **same matrix**
(`matrices/WRAN_irreg_384_256.csv`, verified identical shape/degree profile
to `external_ref/ldpc_rl/matrices/wran_384_256.mat`: 128×384, row degree
10–11), `z=1` (one cluster per check node — the same clustering granularity
as this quartile run and as `reldec_test.m`). Config `c6c6fa2e0a…`, 500
training episodes, `l_max=5` for both train and eval. Crucially, `l_max=5`
in `rl/decoder/sequential.py` means **5 full sweeps of 128 scheduled CN
updates = 640 actions total** — the *same* eval decoding budget as this
quartile run's `m*maxIter = 128*5 = 640`. Matrix, clustering granularity, and
eval action budget are matched; this is a fair head-to-head.

| SNR (dB) | Python `reldec` BER | Python `reldec` FER | Quartile-LLR BER (k=4) | Quartile-LLR FER |
|---|---|---|---|---|
| 1 | 0.0769 (96700 fr.) | 0.9666 | 0.0974 | 1.0 |
| 2 | 0.0160 (96600 fr.) | 0.3323 | 0.0728 | 1.0 |
| 3 | 0.000182 (96600 fr.) | 0.00570 | 0.0510 | 1.0 |
| 4 | 2.2e-7 (96600 fr.) | 1.0e-5 | 0.0333 | 1.0 |

**The gap widens sharply with SNR.** At 1 dB the two are within ~25% of each
other. By 3 dB, Python `reldec` is essentially error-free (BER ≈ 2×10⁻⁴,
FER ≈ 0.6%) while the quartile architecture is still at 5% BER with every
frame failing. By 4 dB the gap is ~5 orders of magnitude in BER. **The
quartile-average-LLR state never reaches the waterfall region in this SNR
range**, while hard-decision RELDEC clearly does with the same action budget.

This is despite the quartile run using **60× more training episodes** (30000
vs. 500) — so the gap is not explained by under-training. The most likely
architectural explanation: collapsing each check node's 10–11 raw neighbor
LLRs into k=3–5 *group averages* throws away exactly the fine-grained
per-neighbor sign information that lets hard-decision RELDEC's Q-table tell
"almost converged" states apart from "still noisy" ones — averaging can hide
a single still-wrong neighbor inside a satisfied-looking group mean, so the
policy has less signal to detect and finish off near-converged codewords.
This is a plausible read of the numbers, not something instrumented directly
in this run.

Two confounds worth flagging rather than glossing over:

1. **Training procedure differs**, not just episode count. Python `reldec`'s
   `train_episode()` forces each cluster to be scheduled *exactly once per
   sweep* (`available_clusters` set, removed as each is picked) for `l_max=5`
   sweeps. The quartile trainer instead follows `reldec_test.m`'s own
   convention: `lmax=50` free ε-greedy action picks per episode, with
   repetition allowed and no forced coverage of all clusters. This is a real
   difference in the training distribution, inherited from which MATLAB
   reference script the reward was copied from — not a bug, but not a
   controlled ablation of the state encoding alone either.
2. **BER denominator matches, checked directly.** `rl/decoder/engine.py`
   computes `bit_errors / (frames * n)` — all `n=384` bits per frame, same
   convention the quartile eval script uses. Not a confound.

Bottom line: on the numbers actually produced here, the quartile-average-LLR
state is a substantially weaker scheduler than hard-decision RELDEC on this
matrix at this action budget, and k (3 vs 4 vs 5) doesn't change that
conclusion.
